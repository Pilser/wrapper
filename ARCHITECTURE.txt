WRAPPER ARCHITECTURE
Detailed Module Breakdown with Plugin-First Design
===================================================


OVERVIEW
--------

The wrapper is a Rust-based orchestrator that manages Firecracker microVMs
for tenants. Every crate is designed plugin-first: plugins can access,
extend, or override any functionality. Tenants belong to CATEGORIES
(robotics, painting, music, staff, etc.) and each category gets a VM
optimized for that domain. A comprehensive TELEMETRY system tracks every
event, error, and latency for full system observability.

Plugin API:
  - EventBuilder: create custom event types
  - emit(): emit custom events from plugins
  - FileWriter: configure file output
  - BroadcastServer: subscribe to live telemetry stream
  - Metrics: register custom metrics (counters, gauges, histograms)
  - Hooks: OnEventEmitted, OnFileFlushed, OnBroadcastSent, OnMetricRecorded
  - Plugins can emit custom telemetry events
  - Plugins can register custom metrics
  - Plugins can subscribe to telemetry streams

================================================================================
TELEMETRY FILE OUTPUT
================================================================================

Daily JSON files stored at configured path:

  /var/log/wrapper/telemetry/2026-09-06.json
  /var/log/wrapper/telemetry/2026-09-07.json
  /var/log/wrapper/telemetry/2026-09-08.json

Each file is a JSON array of events:

[
  { "id": "evt_001", "timestamp": "...", ... },
  { "id": "evt_002", "timestamp": "...", ... },
  ...
]

File rotation:
  - New file created at midnight (or on first event of new day)
  - Old files optionally compressed to .json.gz
  - Configurable retention period (delete files older than N days)

Buffer and flush:
  - Events buffered in memory (configurable buffer size)
  - Flushed to disk on: buffer full, timer interval, or shutdown
  - Configurable flush interval (default: 5 seconds)


================================================================================
TELEMETRY BROADCAST (LIVE DASHBOARD)
================================================================================

When broadcast is enabled, events are streamed live to connected dashboards
via WebSocket or SSE.

Dashboard connects to: ws://wrapper:8081/telemetry

Dashboard can subscribe to specific event types:

  { "action": "subscribe", "events": ["vm.*", "auth.login.*"] }
  { "action": "subscribe", "levels": ["error", "critical"] }
  { "action": "subscribe", "tenants": ["tenant_xyz"] }
  { "action": "unsubscribe", "events": ["vm.*"] }

Events are pushed in real-time as they occur. Dashboard receives the same
JSON structure as written to disk.

Throttling:
  - Rate limit per client (events per second)
  - Backpressure handling (slow clients get sampled events)


================================================================================
TELEMETRY CONFIGURATION
================================================================================

[telemetry]
enabled = true
output = "both"

[telemetry.disk]
path = "/var/log/wrapper/telemetry"
filename_pattern = "telemetry_{date}.json"
buffer_size = 1000
flush_interval_seconds = 5
compress_old_files = true
retention_days = 30

[telemetry.broadcast]
bind_address = "0.0.0.0"
port = 8081
protocol = "websocket"
max_clients = 10
events_per_second_per_client = 100
auth_required = true

[telemetry.metrics]
enabled = true
collection_interval_seconds = 10
track_latency_percentiles = [50, 95, 99]

[telemetry.filters]
exclude_from_disk = ["metric.gauge", "metric.counter"]
min_level = "info"


================================================================================
TELEMETRY INTEGRATION WITH OTHER CRATES
================================================================================

Every crate emits telemetry events at key points:

vm crate:
  - vm.boot.started before boot, vm.boot.completed on success, vm.boot.failed on error
  - vm.shutdown.started/completed/failed
  - vm.idle.detected when idle timeout reached
  - span.completed for every operation with duration

proxy crate:
  - proxy.request.received when request arrives
  - proxy.request.forwarded when sent to agent
  - proxy.request.completed when response received
  - span.completed for request roundtrip latency

auth crate:
  - auth.login.success/failed on login attempts
  - auth.token.created/expired/revoked
  - auth.permission.denied on unauthorized access

supervisor_server crate:
  - supervisor.connected/disconnected
  - supervisor.heartbeat.received/missed
  - supervisor.tool.called/completed/failed
  - supervisor.deployment.sent/acknowledged/failed

db crate:
  - db.query.started/completed/failed with duration
  - db.write.started/completed/failed with duration

plugin_host crate:
  - plugin.loaded/unloaded/reloaded
  - plugin.error on plugin failure

All crates use the same telemetry instance. Configuration is centralized.


================================================================================
TELEMETRY QUERY AND ANALYSIS
================================================================================

The telemetry crate provides query capabilities for the admin dashboard:

  - Search events by: type, level, tenant_id, time range, tags
  - Aggregate metrics: requests per minute, error rate, average latency
  - Export: JSON, CSV for external analysis
  - Real-time: subscribe to live events via broadcast

Admin dashboard endpoints:
  GET /admin/telemetry/events?type=vm.*&level=error&from=...&to=...
  GET /admin/telemetry/metrics?metric=active_vms&from=...&to=...
  GET /admin/telemetry/stats?from=...&to=...
  GET /admin/telemetry/export?format=json&from=...&to=...
  WS  /admin/telemetry/live

================================================================================
CATEGORY-BASED DEPLOYMENT
================================================================================

When a tenant is assigned to a category (or changes category), the wrapper
deploys a package to the VM based on that category.

Deployment package includes:
  1. VM TEMPLATE — which rootfs/kernel to use
  2. SUPERVISOR PLUGINS — .so files for the supervisor itself
  3. AGENT PLUGINS — .so files or tools for the agent
  4. CONFIG FILES — configuration for agent, memory binary, MCP servers
  5. BINARIES — additional tools or programs the category needs
  6. COMMANDS — scripts to run after deployment (setup, initialization)

Example category configurations:

  Category: "robotics"
    VM Template: robotics-template (has ROS, Gazebo, Arduino tools)
    Supervisor Plugins: robotics_monitor.so
    Agent Plugins: robotics_guide.so, electronics_tool.so
    Config Files: agent_robotics.conf, ros_config.yaml
    Commands: initialize_ros.sh, test_motors.sh

  Category: "painting"
    VM Template: painting-template (has Blender, GIMP, color tools)
    Supervisor Plugins: art_monitor.so
    Agent Plugins: painting_guide.so, color_theory.so
    Config Files: agent_painting.conf, palette_defaults.json
    Commands: initialize_canvas.sh

  Category: "staff"
    VM Template: staff-template (has dashboard tools, reporting, oversight)
    Supervisor Plugins: staff_monitor.so, audit_plugin.so
    Agent Plugins: reporting_tool.so, oversight_tool.so
    Config Files: agent_staff.conf, dashboard_config.json
    Commands: initialize_staff_dashboard.sh


================================================================================
VM MIGRATION ON CATEGORY CHANGE
================================================================================

When a tenant changes category:

1. Admin (or tenant) requests category change
2. Wrapper looks up new category's VM template
3. If different template:
   a. Shutdown current VM (data disk stays on host)
   b. Boot new VM with new template + same data disk
   c. Deploy new category's plugins, configs, files to new VM
   d. Update tenant record: category_id, vm_template_id
4. If same template:
   a. Just deploy new category's plugins, configs, files to existing VM
5. Data on disk (memory, history, projects) persists unchanged
6. Only the VM environment changes to match new category


================================================================================
COMMUNICATION FLOW: SUPERVISOR → WRAPPER
================================================================================

[Agent inside VM]
       |
       | MCP tool call (unix socket)
       v
[Supervisor inside VM]
       |
       | MCP request (network: save_memory, get_profile, etc.)
       v
[supervisor_server in Wrapper]
       |
       | validate tenant_id matches this VM
       v
[db crate] — read/write tenant DB
       |
       v
[supervisor_server] — return response to supervisor
       |
       v
[Supervisor] — return to agent


================================================================================
STARTUP FLOW
================================================================================

1. Load config.toml
2. Initialize telemetry
3. Initialize logging
4. db::global::init()              → open global DB, run migrations
5. db::tenant::init()              → ensure tenants/ folder exists
6. vm::templates::init()           → load registered VM templates
7. vm::manager::init()             → check Firecracker binary
8. network::ip_pool::init()        → load IP range from config
9. supervisor_server::start()      → listen for supervisor connections
10. auth::init()                   → load auth config
11. proxy::start()                 → start client proxy
12. admin::init()                  → load categories and deployment configs
13. plugin_host::init()            → load all plugins
14. plugin_host::watcher::start()  → watch plugins/ for changes
15. telemetry::broadcast::start()  → start live telemetry server
16. Enter event loop               → run until shutdown
